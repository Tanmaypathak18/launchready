LaunchReady

LaunchReady is a small open-source kit for open models on NVIDIA GPUs.

Its job is to help a team know whether a new open model will run on NVIDIA GPUs before launch.

It projects memory from a model's published files, then tests those projections on real GPUs and real quickstarts.

What I found

Every number below is tagged measured or projected and links to its file. Measured results are from 2026-11-03 unless noted.

4–6%measured vs projected gap

The memory math held up on standard models

For one dense model and one mixture-of-experts (MoE) model, projected user capacity landed within 4–6% of measured, slightly on the cautious side.

  • Qwen3-4B (dense), users at 4,096 tokens: projected 7.12, measured 7.41, a gap of −3.9%
  • OLMoE-1B-7B (MoE), users at 4,096 tokens: projected 20.22, measured 21.47, a gap of −5.8%
  • Model weights, same two models: −0.9% and −0.1% against measured

Run on 2× Tesla T4 on Kaggle with vLLM 0.32.0.

Evidence: memory_validation.csv · chart · environment · notebook

+133%projected above measured

The hybrid Mamba model broke the math

On granite-4.0-h-tiny, a team sizing from my projection would have expected more than twice the users the engine could hold.

  • Users at 4,096 tokens: projected 118.08, measured 50.58

Two errors multiply to make that miss:

  • confirmed ×1.72, less memory left for users. vLLM's log shows 2.93 GiB per GPU measured against 5.04 GiB projected, because overhead beyond the weights was 3.70 GiB measured, not the 2 GiB the formula assumes.
  • hypothesis ×1.36, each user costs more. The size is known: 124 MB measured against 92 MB projected. The cause is not: how vLLM pages Mamba state is the likely reason, and it is not confirmed.

The tool now warns about this gap, and I did not retune it from one model. Lightning is also a hybrid Mamba model, so its capacity projection carries the same risk.

Evidence: friction log analysis · memory_validation.csv · vLLM log

+16%real file above projection

Lightning's real NVFP4 file is bigger than the math says

The projection treats every weight as 4-bit, but the real checkpoint keeps some tensors at higher precision, so the tools now use real file sizes when they exist.

  • NVFP4 weights: projected 17.24 GiB, measured 20.08 GiB

20.08 GiB is the file size on Hugging Face, read on 2026-11-02, not memory measured on a GPU.

Evidence: brief, hardware table · friction log

~6.1bits per weight

"Q4_K_M" GGUF files are not what the name suggests

Three Lightning files with that name store about 6.1 bits per weight, so they take more memory than the label implies.

  • Read from file headers: measured 6.19 (bartowski), 6.14 (unsloth), 6.08 (AtomicChat)
  • What my tool assumes: projected 4.85 bits per weight, or 18.58 GiB against a 23.73 GiB file measured (bartowski)

No GPU involved, and no weights downloaded. launchready fit still uses 4.85, which the checklist marks not ready; the brief and recipes use real file sizes instead.

Evidence: bartowski header · unsloth header · AtomicChat header · friction log

3quickstarts that broke

Following the model cards as written hit three breaks

I ran published commands word for word, the way a first-time developer would, and each of these stopped them from getting an answer.

  • Qwen3-4B card, vLLM command. Fails on vLLM 0.32.0 with an unrecognized --enable-reasoning flag, exiting after 30 s measured, on 2× Tesla T4.
  • Qwen3-4B card, Python snippet on a 16 GB Mac. Offloads to disk with only a one-line log notice, and printed no answer before the 2,700 s cap measured. The same snippet worked on 2× Tesla T4 in 115 s measured.
  • Lightning NVFP4 card, llama.cpp recipe. Asks for :Q4_K_M, but the official GGUF repo has no such file, so it exits after 6 s measured.

Evidence: vLLM log · vLLM write-up · Mac log · Mac write-up · Kaggle summary · llama.cpp log · NVIDIA card, official repo line · llama.cpp write-up

The Lightning brief and readiness checklist

I applied this work to one launch: NVIDIA Nemotron 3.5 Lightning on a single RTX 5090. The verdict today is not ready, mostly because nothing has been measured on a 5090.

27 checks in all. These are counts of checklist items from evidence in the repo, not hardware measurements. The one ready item is a document check.

  • Readiness checklist: each check with its status, evidence and what closes it.
  • Lightning model brief: capabilities, hardware needs, engine support and ecosystem impact, projected unless marked measured.

What is measured vs projected

measured

  • Memory on 2× Tesla T4: driver 580.178.04, CUDA 13.0, vLLM 0.32.0. Weights come from vLLM's load log, because a separate Transformers check crashed on my own bug; that fix was not re-run on a GPU.
  • GGUF headers and Hugging Face file sizes, read without a GPU.
  • Quickstart audits, on Kaggle 2× T4 and a MacBook Air M4 with 16 GB.

projected

  • Everything about Lightning running on an RTX 5090. With vLLM: 20.08 GiB of weights, 0.28 GiB per 40,960-token conversation and about 18 conversations (formula and table).
  • With a GGUF file: about 6.0 GiB left with 8 slots, from a 23.73 GiB file (formula and table).

Not measured

  • Lightning on an RTX 5090 has not been run. No speed, memory or quality number on this page comes from a 5090 (progress).
  • The kit is dry-run only, on Tesla T4 with Qwen3-4B, not Lightning. Those outputs prove the scripts run and are not headline results.
  • Fixes from the dry runs are confirmed on T4 only, not on Lightning, and the status for lost requests has never triggered on a GPU (what each fix changed).
  • Chat template, tool calling, a long soak run and a tokenizer comparison have not been tested (list).

How this applies to open-model launches

Seven areas of launch work, and what the project does in each.

  1. Enablement and launch readiness with model buildersA checklist like this one gives builders confirmed defects and the fix that closes each one.
  2. Tracking and summarizing releasesA release radar and a one-page brief cover capabilities, hardware needs and ecosystem impact.
  3. Requirements, launch plans and checklistsWhat testing finds becomes requirements with acceptance criteria and owners.
  4. Inference, evaluation and deploymentPinned recipes and benchmark scripts can repeat for each launch; here they have run only as a dry run.
  5. Feedback into recurring issues and requirementsDeveloper threads are read by hand, grouped by root cause and ranked by severity.
  6. Testing developer workflows, notebooks and PythonQuickstarts are run word for word, with each break logged in a friction log and runnable notebooks.
  7. Developer docsThe recipe README shows the writing style, with every number labeled.
