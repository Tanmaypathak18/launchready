# Developer feedback on Hugging Face → requirements: NVIDIA Nemotron 3.5 Lightning

collected November 3, 2026

**Scope.** 36 GitHub issues and Hugging Face discussions opened between August 1 and November 3, 2026 (Lightning was released August 11). Sources: `vllm-project/vllm`, `ggml-org/llama.cpp`, `ollama/ollama`, NVIDIA's Lightning repos on Hugging Face (BF16, NVFP4, NVFP4-DSpark) and the two most-downloaded community GGUF repos (ggml-org, Unsloth). Issues about sibling models (Nemotron 3 Nano, 3.5 Bolt, 3 Puzzle) are included only when the root cause is the shared `nemotron_h` / `nemotron_h_moe` architecture. Every thread is listed in the [evidence log](#evidence-log).

**Method.** Searched each engine repo for `Nemotron 3.5 Lightning`, `nemotron-3.5`, `nemotron_h` and `NemotronH`; listed every discussion on the Hugging Face repos; read each thread; tagged it with one primary theme and a severity; ranked themes by severity first, then thread count.

**Severity scale.** *Wrong output*: the model answers fluently but incorrectly with no error (worst, because nobody notices). *Blocks*: won't load, start or stay up. *Slows*: works, but a feature is off or slower than expected. *Cosmetic*: annoyance only.

**Counts.** `# issues` counts threads, not distinct bugs. Where several threads describe one defect, the requirement says so.

### Below the cut

- **Chat template / tool calling (2 threads).** With the `qwen3_coder` parser, string arguments lose a trailing newline, which silently breaks file-writing and edit tools ([vllm#62078](https://github.com/vllm-project/vllm/issues/62078)); multi-turn tool-call harnesses truncate below `max_tokens=8192` ([NVFP4 #11](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-NVFP4/discussions/11)). Severe for coding agents but only two reports; revisit if more appear.
- **Out of memory.** No Lightning-specific OOM reports in the window. The one MoE OOM found ([vllm#60471](https://github.com/vllm-project/vllm/issues/60471)) is Nemotron 3 Super on 8× B200, so it was left out.
- **Out of scope** (not NVIDIA GPUs, or cosmetic): AMD Strix Halo stalls ([ollama#17692](https://github.com/ollama/ollama/issues/17692)), `/save` failing for this model ([ollama#17735](https://github.com/ollama/ollama/issues/17735)).

## What this changes in LaunchReady

These findings shaped the launch kit.

1. **Phase 1 calculator.** For Lightning, "GGUF Q4_K_M ≈ 4.8–4.9 bits/weight" (section 6.1) is wrong for the expert tensors, which are about 93% of the weights: they fall back to `Q5_0` (5.5 bits/weight). Read the tensor types from the GGUF header, or check against the real file size, before publishing a projection ([unsloth GGUF #1](https://huggingface.co/unsloth/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-GGUF/discussions/1)).
2. **Phase 5 vLLM recipe on the 5090.** Two reports say the card's `--kv-cache-dtype fp8` breaks startup on SM12x and that removing it works. Try the card's command first (that's the finding), then without FP8 KV, and record both. The memory projection should use a BF16 KV cache for the working config.
3. **Phase 5 Ollama benchmark.** Ollama forces one parallel slot for `nemotron_h_moe`, so Ollama runs at concurrency 8 and 32 measure queueing, not batching. Benchmark Ollama at concurrency 1, and run `llama-server -np 8` directly for the concurrent GGUF points.
4. **Phase 5 benchmark settings.** Run with prefix caching off for headline numbers (it costs 13–16% with no cache hits) and pin the vLLM version: decode speed moved 16% between v0.28 and v0.29 on one Blackwell device.
5. **Phase 5 quality check.** Older Lightning GGUFs use the wrong pre-tokenizer (`pixtral` instead of `tekken`). Record `tokenizer.ggml.pre` for the GGUF you benchmark, since it can shift GSM8K/IFEval results against NVFP4.
